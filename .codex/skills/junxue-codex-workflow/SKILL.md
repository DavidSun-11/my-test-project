# 君雪 CodeX 工作流

## 一、适用范围

这个 Skill 适用于君雪个人网站的所有 CodeX 修改任务，包括：

- UI 精修
- Bug 修复
- Supabase / 数据库相关开发
- Live2D 功能与菜单
- 文案修改
- 页面优化
- 图片素材接入
- SVG / 装饰素材
- 视觉方向落地

每次开始任务时，先读取 `AGENTS.md`；如果 `PROJECT_CONTEXT.md` 存在，也必须读取。再读取本 Skill 和本次任务直接相关的其它 Skill / 文档。

## 二、任务开始前仓库同步检查

这项检查适用于依赖最新仓库内容，或需要修改仓库文件的任务。纯解释、纯分析且不依赖最新文件内容的任务不必重复拉取。

每次开始这类任务前，必须先运行：

```bash
git status --short
git branch --show-current
git fetch origin --prune
git rev-parse HEAD
git rev-parse origin/main
```

检查规则：

- 如果工作区干净、当前分支为预期分支，并且本地可以安全 fast-forward 到 `origin/main`，先执行：

  ```bash
  git pull --ff-only origin main
  ```

- 如果 `HEAD` 已等于 `origin/main`，确认已同步后再继续任务。
- 如果需要确认是否可 fast-forward，可使用 `git merge-base --is-ancestor HEAD origin/main`；只有本地 `HEAD` 是 `origin/main` 的祖先时，才允许执行 `git pull --ff-only origin main`。
- 如果工作区有未提交修改、本地与远程发生分叉、当前分支不是预期分支，或无法 fast-forward，停止同步并向用户报告。不得擅自处理。
- 为了同步，禁止执行 `git reset --hard`、`git clean`、自动 `git stash`，也不得覆盖、删除或隐藏用户本地修改。

当用户明确说明某个文件已经上传到 GitHub 时，不得只检查本地文件系统，也不得直接判断文件不存在。必须先执行：

```bash
git fetch origin --prune
git ls-tree -r --name-only origin/main -- <目标路径>
```

- 如果目标文件存在于 `origin/main`、但当前本地不存在，先按上述安全规则同步最新远程提交，再次验证本地目标文件。
- 不得因为本地仓库版本过期，就擅自使用旧素材、相似素材或其它文件替代用户指定的新素材。
- 同步完成后，确认当前 `HEAD`、`origin/main` 和目标文件状态，再继续实施任务。

## 三、通用工作规则

- 不要重做网站。
- 只修改本次需求相关文件。
- 不要影响现有功能。
- 不要顺手改无关模块。
- 不要引入重型前端框架。
- 不要新增外部 CDN。
- 不要自动打开网页。
- 不要截图。
- 不要浏览器验收。
- 用户自己测试。
- 修改完成后必须 commit 并 push 到 `origin/main`。
- 不要只停留在本地 `main ahead` 状态。
- push 后必须汇报：修改文件、每个文件改了什么、commit id、手动验证方法、兼容性注意点。

## 四、任务分流规则

### 1. UI / 视觉任务

必须阅读：

- `DESIGN_SYSTEM.md`
- `UI_COMPONENT_RULES.md`
- `.codex/skills/junxue-ui-polish/SKILL.md`
- `.codex/skills/junxue-codex-workflow/SKILL.md`

必须遵守：

- 必须改真实生效 DOM，不要只新增 class。
- 不要默认灰色按钮。
- 不要裸文本堆叠。
- 不要文字和数值黏连。
- 不要只做表面样式，肉眼必须有明显变化。
- 不要改业务逻辑，除非本次明确要求。
- 修改 JS / CSS / 注入样式后必须更新缓存版本号。
- 必须检查手机端不横向溢出。

### 2. Bug 修复任务

- 只修本次 Bug。
- 不顺手美化。
- 不引入新功能。
- 不扩大修改范围。
- 优先定位真实原因，不要用粗暴隐藏问题的方式假修复。

### 3. Supabase / 数据库任务

必须阅读：

- `SUPABASE_SETUP.md`
- `.codex/skills/junxue-codex-workflow/SKILL.md`

必须遵守：

- 遵守 RLS / RPC 安全边界。
- 不能从前端查询 `auth.users`。
- 不能暴露完整邮箱。
- 不能暴露 `user_id`。
- 不能暴露完整 UUID。
- 不能把 `service_role key` 放到前端。
- 前端只使用 anon / publishable key。
- 普通用户不能越权读取管理员数据。

### 4. Live2D 任务

必须重点保护：

- 菜单结构
- 菜单点击逻辑
- 弹窗定位
- 弹窗尺寸
- 手机端宽度
- 现有入口分组
- 天气 / 占卜 / 听歌 / 评分竞猜 / 咨询 / 认识君雪 / 意见箱等入口

不要因为样式修改导致：

- 菜单点不开
- 弹窗跑位
- 菜单被撑大
- 页面横向溢出
- 伪元素挡点击
- 其它功能失效

### 5. 素材 / 图片 / SVG 任务

必须遵守：

- 优先 CSS + 小 SVG + 少量小图。
- 不要新增大 PNG / JPG。
- 不要让素材体积失控。
- SVG 必须自绘。
- SVG 不能包含 `script`。
- SVG 不能包含 `onload` / `onclick`。
- SVG 不能外链。
- SVG 不能包含 `image` 引用。
- 单个 SVG 尽量小于 15KB。
- 新增素材总大小尽量可控。

### 6. 文案任务

- 只改文案，不改业务逻辑。
- 保持君雪网站的温柔、自然、陪伴感、梦幻感。
- 不油腻，不像后台，不像诈骗页面。

## 五、缓存版本号规则

- 修改 JS / CSS / 注入样式后，必须同步更新相关缓存版本号。
- 尤其关注：
  - `index.html`
  - `price.html`
  - `assets/live2d-loader.js`
  - `assets/live2d-interactions.js`
  - `assets/live2d-interactions-lazy.js`
- 目的是避免 GitHub Pages 继续加载旧文件。

## 六、常用检查命令

基础检查：

```bash
git diff --check
node --check assets/live2d-loader.js
node --check assets/live2d-interactions.js
node --check assets/live2d-interactions-lazy.js
```

如果本次修改了其它 JS 文件，也要对对应 JS 执行 `node --check`。

如果新增 SVG，需要执行：

```bash
rg "<script|onload=|onclick=|http://|https://|<image" assets
```

如有命中，必须确认并处理安全问题。

## 七、精简命令规则

以后用户给 CodeX 的命令可以只写：

- 读取 `AGENTS.md`
- 读取 `PROJECT_CONTEXT.md`
- 读取 `.codex/skills/junxue-codex-workflow/SKILL.md`
- 读取本次任务相关 skill
- 本次目标
- 修改范围
- 禁止事项
- 检查命令
- commit + push 要求

不要要求用户每次重复整套长规则。本 Skill 已经固化通用规则、UI 精修规则、素材风格规则、检查规则和汇报规则。

## 八、UI 美化与素材风格规则

### 1. 不要只做普通风格

素材和美化任务不能每次都默认成：

- 深蓝渐变
- 普通星空
- 普通玻璃圆角卡片
- 普通冰蓝描边
- 普通悬浮按钮
- 大面积空背景
- 没有层次的水晶装饰
- 模板站感
- 后台系统感
- 页游充值页感
- 廉价二次元感

### 2. 每次先做多方向分叉

每次素材 / 视觉任务，除非用户明确指定某一种风格，否则应先做多方向分叉，至少给出 3 个差异明显的方向。

每个方向都应说明：

- 适合哪个页面
- 主要颜色
- 主要元素
- 氛围关键词
- 优点
- 风险点
- 是否适合手机端
- 是否容易与真实 DOM 融合

### 3. 素材落地原则

- 不要直接把整张效果图当网页。
- 不要把标题、文字、按钮、输入框、二维码、表单做死进图片。
- 图片只负责背景、氛围、边框、装饰。
- 标题、文案、按钮、表单、二维码都必须用真实 DOM。
- 素材要为 DOM 服务，而不是反过来让 DOM 迁就图片。
- 页面要有留白，方便后续叠加真实内容。
- 素材不能喧宾夺主，不能让正文难以阅读。

### 4. 复杂 UI 视觉素材落地规则

UI 精修、新页面、背景、卡片、菜单框、徽章、装饰道具等任务，不要理解成只能用 CSS 或 SVG。应根据视觉复杂度选择合适方式：

- CSS：用于布局、玻璃质感、渐变、阴影、响应式、简单光效。
- SVG：用于角花、吊坠、徽章、花枝、星盘线条、边框、小图标、菜单装饰。
- 小 PNG / WebP / AVIF：用于复杂背景、月夜湖泊、庭院氛围、灯笼、花枝、复杂光影、难以用 CSS/SVG 高质量复刻的场景。
- CSS mask / clip-path / filter：用于异形边框、水晶切角、发光遮罩、装饰裁剪。
- Canvas：仅在确实必要且轻量时使用，例如湖面微波纹、星尘粒子等；不能滥用，不能拖慢首页。
- CodeX 自制轻量素材：如果仓库没有合适图片或装饰素材，可以自己生成、绘制或创建一个相近的小素材加入仓库使用。

如果参考图里有明确复杂道具，例如水晶吊坠、花枝、花瓣、灯笼、月亮、湖面倒影、星盘线条、珠宝徽章、水晶卡牌、玻璃雕花边框、庭院剪影、菜单装饰角、评分竞猜宝石卡牌，而仓库没有对应素材，CodeX 不要直接用圆点、粗线、emoji 或普通渐变代替。应优先判断：

- 是否可以用自绘 SVG 表现。
- 是否应该生成一个小 PNG / WebP / AVIF 静态素材。
- 是否可以用 CSS mask / clip-path 辅助。
- 是否需要用户提供更准确素材。
- 是否可以先做一个低风险简化版，并明确说明简化损失了哪些效果。

如果任务明确是 UI 精修或新页面视觉落地，且仓库没有合适素材，允许 CodeX 自己创建相近的轻量素材并放入仓库使用。建议路径：

- `assets/ui/`
- `assets/images/`

自制素材命名要求：

- 使用英文小写或清晰英文名。
- 不要使用含义不明的 `final1`、`new2`、`test3`。
- 不要删除原有中文名素材。
- 如果中文路径有兼容风险，可以复制一份英文名使用。

自制 PNG / WebP / AVIF 素材必须遵守：

- 优先压缩。
- 不新增超大图片。
- 不把整页做成图片。
- 不把文字、按钮、输入框、二维码、积分、昵称、日期等做死进图片。
- 图片只负责背景、氛围、边框、装饰、复杂道具。
- 真实内容必须继续由 DOM + CSS + JS 渲染。
- 首页素材尤其要控制体积，避免页面更卡。
- 不使用外链图片。
- 不使用外部 CDN。
- 不引入重型前端框架。

以后遇到复杂参考图，不允许用以下方式敷衍：

- 用几个圆点代替水晶吊坠。
- 用普通 border 代替雕花边框。
- 用 emoji 代替徽章。
- 用普通渐变代替珠宝卡牌。
- 用深蓝色块代替月夜湖泊背景。
- 用随机星点代替星盘线条。
- 用普通圆角按钮代替精致菜单槽位。
- 用粗糙 CSS 圆形代替花枝、灯笼、水晶装饰。

即使允许使用自制素材，也必须保留真实 DOM 底线：

- 标题是真实 DOM。
- 文案是真实 DOM。
- 按钮是真实 DOM。
- 表单是真实 DOM。
- 二维码使用真实二维码图片，不是假二维码。
- 昵称、积分、评分、日期、评价内容等动态数据必须真实渲染。
- 不能把整张 UI 效果图当网页。

复杂 UI 任务动手前，应先在回复或执行计划里拆解：

- 哪些部分用真实 DOM。
- 哪些部分用 CSS。
- 哪些部分用 SVG。
- 哪些部分适合小 PNG / WebP / AVIF。
- 哪些素材仓库已有。
- 哪些素材需要自制。
- 哪些地方不能用圆点或粗线替代。

### 5. 当前主要页面推荐视觉方向

#### A. 老板注册页

推荐方向：

- 淡紫珍珠花晶
- 温柔邀请函
- 梦幻女系玻璃面板
- 纱帘
- 水晶吊坠
- 冰蓝柔光
- 甘雨陪伴感

避免：

- 普通后台注册表单
- 整图硬塞
- 假输入框
- 廉价粉紫
- 过于通用的玻璃卡片

#### B. `contact.html` 支付解锁页

推荐方向：

- 珍珠紫白
- 水晶信笺
- 柔和可信
- 轻梦幻
- 支付卡清楚
- 二维码区域干净
- 主按钮建议 CSS 实现

避免：

- 像诈骗页
- 像页游充值页
- 假二维码
- 金光乱闪
- 太黑太压抑
- 太花导致二维码难扫

#### C. Live2D 菜单框

推荐方向：

- 星尘夜湖
- 深蓝玻璃
- 银蓝微光
- 7 个纵向按钮槽
- 湖面微波纹
- 倒影轻晃
- 轻盈精致，不厚重

避免：

- 大灰弹窗
- 小图片贴片
- 按钮太厚
- 菜单过大
- 装饰层挡点击
- 只是贴图而不做可伸缩 UI

#### D. 评分竞猜

推荐方向：

- 星空冰湖幻想服务台
- 冰晶徽章
- 铜 / 银 / 金 / 紫晶 / 雾白分级
- 带方向感的水晶铭牌
- 冰湖极光氛围
- 比普通投票卡更精致

避免：

- 普通投票卡
- 默认按钮
- 徽章像廉价贴纸
- 背景单调
- 只是换颜色但没有结构变化

### 6. 风格质量要求

每次素材或美化方案都应避免：

- 太普通
- 太空
- 太模板化
- 太像后台
- 太像廉价页游
- 太像随机 AI 图
- 元素堆砌但没层次
- 和真实 DOM 难以融合
- 所有页面都长得一样

每次素材或美化方案都应尽量做到：

- 有主题
- 有辨识度
- 有层次
- 有留白
- 有页面用途区分
- 能承载真实 DOM
- 不抢正文
- 和君雪网站整体气质一致，但不同页面仍有差异化

```markdown
已完成并推送。

修改文件：
- 文件 1：改了什么
- 文件 2：改了什么

检查结果：
- git diff --check：通过 / 未通过
- node --check：通过 / 未通过

Commit：
- commit id 和 message

Push：
- 是否已推送到 origin/main

手动验证：
- 用户应该怎么测

兼容性注意：
- 有无需要注意的地方
```
